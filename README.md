# 豆包客户端模型 · DSH 本机插件

将**本人已登录的豆包 Windows 客户端**中的纯对话入口注册成 DeepSeek Harness 模型供应商 `doubao-client`，提供真实订阅额度查询和独立用量台账。

> **接入范围：客户端检测到的 12 个入口全部接入。** 快速、专家走客户端原生对话入口；`自动`、`豆包 2.1 Lite/Pro`、`DeepSeek V4.1 Flash/V4 Pro`、`Kimi K3/K3.1 Pro/K3.1 Pro 高速`、`GLM 5.3/GLM 5.3 Flash` 这 10 个在客户端只出现在**工作**分支，插件改以**普通对话模式**调用它们，并把它们的**任务型思考码**（`DeepThinkGeneralTask*`）换成普通 Auto 码 —— 这正是 `自动` 与 `豆包 2.1 Pro` 之前报 `moa param check failed` 的真正原因，换码后两者实测都能正常出结果。插件**不启用**豆包原生任务运行时、本地/云沙盒、桌面工具或联网执行。

## 已验证环境与接入方式

- Windows 11，豆包 2.36.6 / Chromium 147，本地安装位置 `D:\doubao\app\Doubao.exe`。
- 使用本人明确允许后启动的**当前豆包客户端**，不是另开未登录网页替代客户端。
- 客户端以 `--remote-debugging-address=127.0.0.1 --remote-debugging-port=19226` 启动；已检查监听地址为 `127.0.0.1`。
- Host 插件通过 CDP 调用客户端自身已有的 bootstrap、聊天 SSE 和订阅查询服务；Cookie、设备参数和登录凭据不离开客户端。
- DSH 原生 `llm.registerAdapter` 挂载 provider，流式返回原生 block / finish / 已知 usage，未修改 DSH 核心或豆包安装文件。
- 不提供裸露的 OpenAI 公网代理服务；管理接口复用 DSH 已认证连接的 `/api/doubao-client`。

## 安装与前端入口

本插件是 plain JavaScript bundle，无构建步骤、无第三方运行时依赖。支持通过 DSH Plugin Manager 安装发布的 `.tgz` 包，或安装源码目录。测试环境为 DSH Desktop 0.2.1-rc.2 / Node.js 22+；不承诺兼容所有 DSH 发行版本。

Host 侧是否即时生效，以 Plugin Manager 的 `application` 与 `warnings` 为准。若模型可用但设置页入口没有出现，可先保存工作，再正常重启 DSH 后检查。曾在测试环境观察到运行时安装后前端入口加载不一致，不能据此保证所有版本的页面刷新行为。重启插件会清空内存续接状态，但不会删除本地用量台账。

安装不包含登录凭据或客户端程序；使用前需自行安装豆包，并由本人登录、明确允许开启本机调试端口。

## 图片是怎么支持的（以及怎么验证的）

1. **DSH 侧**：插件声明 `inputModalities: ['text','image']`（只对实测通过的模型），并用 `imageRequestTarget()` 告诉 DSH 想要的请求版图片规格；真正取字节走 `attachments.readImageRequest(ref, target)`，由 DSH 负责缩放和缓存，插件不自己去读本机文件。
2. **客户端侧**：图片字节送进客户端页面后，用**客户端自己的上传通道**（其贴图处理器用的同一个 `UploaderService`，`scene='5'`、`type=2`）上传，拿到 `tos-cn-i-a9rns2rl98/<hash>.png` 形式的 uri。**协议没有 base64 通道**——这点是我抓真实请求确认的，不是推断。
3. **消息结构**：图片以 `block_type 10052` 的 `attachment_block` 发出，字段照抄客户端自己的做法（`type/identifier/image.uri/image_ori.width/height/format/upload_status/progress/...`），正文文本块照常随行。
4. **验证方法**：造一张内容确定的图（蓝色底 + `DSH-7391` + 三个圆点），让每个模型"只回复图里的英文和数字"。**10 个模型答出 `DSH-7391`**；`GLM 5.3 Flash` 与 `DeepSeek V4 Pro` 返回上游 `rate limited`（710022004）——复测纯文字同样是限流，说明是模型级限流而非图片问题，所以这两个的图片能力**未验证、不声明**。

## 关于客户端的「工作」模式（本地电脑 / 云电脑）

客户端底部有 `对话` / `工作` 两个分支，`工作` 下还能选 `工作任务 · 本地电脑` 和 `工作任务 · 云电脑`。这里要说清一件事：

- **`工作` 模式不是"多出几个模型"，而是"换执行方"。** 模型还是那些模型；区别是任务由**豆包自己的 agent** 在一个沙盒里执行——可以读写工作目录、跑命令、操作本机（`本地电脑`）或云端环境（`云电脑`）。它有客户端自己的权限模式（例如"按需确认"）。
- 我用真实抓包确认了这条链路需要什么：请求里必须带 `general_task_param.action`、`agent_task_param`（`runtime_type`、`sandbox_auth_type`、`device_name`、`workspace`、`local_app_id`、`local_device_id`）、以及 `client_option` 里的 `enable_sandbox`、`sandbox_id`、`client_env_id`、`shared_folder_path`。这些 id 是**客户端创建任务会话时自己申请并持有的沙盒实例**。
- **所以本插件不接这条链路。** 如果让 DSH 去驱动它，豆包 agent 就会在 **DSH 之外**直接操作这台电脑：DSH 的工具审批、权限模式、操作审计全部绕过，额度与状态也不受 DSH 管理。这正好是插件一开始就写明的边界（不代执行豆包原生桌面工具）。
- **DSH 里等价的能力**是：模型只负责判断和产出，动作交给 **DSH 自己的工具**（读文件、跑命令、点浏览器……）在 DSH 的权限下执行。本插件的工具适配就是按这个分工做的：模型输出受限的 `dsh_tool_calls` JSON，DSH 校验参数与权限后才执行。
- 如果你确实想让**豆包自己**在本机干活（而不是让 DSH 用豆包模型干活），那直接用豆包客户端更合适；两者混在一起只会让执行权变得不可控。真要接这条链路（例如只取云电脑沙盒结果、不接受本地执行），可以做成显式开关的独立特性，我会先把"哪些字段必须由客户端持有、哪些动作会真的落到本机"逐项实测清楚再动手。

## 使用

### 推荐：设置页首次使用向导（1.8.0）

1. 自行安装豆包 Windows 客户端。打开 DSH **设置 → 豆包客户端模型**，顶部“首次使用与本机授权”会只读检测正在运行的进程、安装信息和常见目录；找不到时可手填自己的 `Doubao.exe` 路径。
2. 若豆包已运行且本机通道可核实，直接复用，不需要重启。若已运行但没有调试通道，请先保存当前任务并从托盘正常退出；插件绝不强退或重启客户端。
3. 豆包未运行时，阅读调试端口风险，勾选**未预选**的明确授权，再点击“授权并启动豆包”。后台直接启动已验证签名的程序，不需要手动找脚本或安装 `pwsh`；豆包自己的窗口可能出现或改变前台焦点。
4. 由本人完成登录、验证码或风控检查，再刷新连接、额度与模型。启动成功只表示本机通道就绪，不代表登录/模型生成已成功。
5. 可选开启“允许以后按已保存授权自动启动”（**默认关闭**）。只有明确使用/解析豆包模型时才可能按需启动；插件加载、模型目录列表、设置页刷新和 `doubao_client_status` 始终只读，不能借此启动。自动启动失败不自动重试、换号或改变端口。
6. 随时可以“撤销授权并关闭自动启动”。撤销不杀掉已有客户端、不关闭已存在的调试端口；若想关闭通道，请本人正常退出豆包并按原方式启动。

路径与启动授权仅保存在本机 `%LOCALAPPDATA%/dsh-doubao-client/startup.json`，不随 npm 包、源码归档或市场材料分发，不含登录凭据。保存路径/授权本身不会启动客户端。未经核实的路径、签名、端口占用或权限问题会阻止启动；发行者证书变化可能需要插件更新，不以关闭校验来绕过。

设置页通过 DSH 已认证连接的独立 setup 路由执行显式操作，并校验同源 Origin、固定动作与参数。只读模型工具不开放 configure/start。Windows 原生查询不设置 ExecutionPolicy Bypass，也不执行用户拼接的 shell 命令；如果机器策略阻止原生查询，将报告诊断失败，不提升权限。

### 手动脚本（可选排障，不再是正常使用的必需步骤）

1. 启动并由本人登录豆包。
2. 如果没有开启通道，先完成豆包当前任务，在系统托盘菜单选择“退出”，再运行：

   ```powershell
   pwsh -NoProfile -File ".\launch-doubao.ps1" -DoubaoPath "C:\path\to\Doubao.exe"
   ```

   该脚本不杀进程、不强行重启、不自动登录、不改快捷方式。若豆包已经运行但没有调试通道，它会拒绝重开并说明正常退出步骤。路径不同可传 `-DoubaoPath`。

3. DSH **设置 → 豆包客户端模型**，点击“刷新连接、额度与用量”。
4. 在对话模型选择器中选 **豆包客户端 · 本机**，然后挑模型：`豆包 · 快速`、`豆包 · 专家`，以及带“（对话模式）”后缀的 10 个工作任务模型。安装不会替你切换当前会话或默认模型。
5. 不使用时正常退出豆包，再以原方式启动，即可关闭这次调试通道。卸载插件不等于关闭豆包的调试端口。

### 工具适配的重要区别

客户端纯聊天协议没有独立 system/developer/tools API。插件把完整 DSH system、角色消息和当前可用工具 schema 序列化为文字；模型需要工具时必须返回严格的 JSON 封装，插件仅将当前可用工具名转换成 DSH `tool-call`。

- 参数 schema 和权限仍由 DSH 校验，插件不自己执行工具。
- 拒绝未知工具名、非对象参数和过多调用。
- 工具结果来自 DSH，插件不会编造；满足安全续接条件时下一轮传新增消息，否则重新发送当前完整历史。
- 这不具有正式模型 API 的角色隔离和原生工具可靠性，适合受监督的轻量交互，不建议用于无人值守高风险写操作。

## 用量与额度：三个不同概念

1. **本地请求台账**：UTC+8 今日 / 默认最近 90 天的请求成功、失败、取消数、输入输出字符数、耗时、按模型汇总。它只统计本插件，不包括客户端原有对话或手动聊天。
2. **服务端 token 用量**：只有上游明确返回可核实的 token 计数时才传给 DSH。当前实测未得到 token 计数，所以显示未知，而不是 0 或虚构的精确数。
3. **订阅额度**：由客户端 `AGWGetSubscriptionQuotaSummary` 实际查询，分近 7 天、5 小时、套餐总量、每月等窗口和订阅/企业/活动赠送来源。它不是 token 数，不是人民币余额；不能用本地字符数反推。

`ceil(字符数 / 4)` 仅为界面中**独立标明的粗略估算**，不会被写入真实 usage，也不用于扣减账户额度。查询失败时显示 unknown；若有上次读数，会保留其原始查询时间并标为 cached，不冒充新结果。

台账位于 `%LOCALAPPDATA%\dsh-doubao-client\usage\`，只保存白名单计数，不含 prompt、回复正文、Cookie、设备 ID 或登录凭据。按日分片，保留最多 90 天；默认单日 1 MiB，上限拒绝并在设置页报告，不无限增长。损坏行/超大文件有诊断，不静默算作完整。`all` 是保留窗口累计，**不是终生累计**。同进程多实例串行写入，不支持多个 DSH OS 进程同时写同一目录。

## 隐私、安全与账号风险

- 非官方集成，与豆包及字节跳动无隶属关系，未获得其认可；可能违反其服务条款或因客户端更新、限流、登录、验证码、风控而失效，请仅用于本人账号并自行评估。
- 不解密登录库、不导出 Cookie、不注入认证令牌、不绕过登录或风控。不修改客户端安装文件。
- **CDP 端口能控制当前豆包账号。** 仅绑定本机也不代表没有风险，本机其他程序仍可能访问。勿转发到局域网/公网，勿用于不可信多用户机器。插件不替你修改防火墙或自动常驻启动。
- 只连接固定的豆包聊天页面；读取模型目录和额度，不读取已有私人聊天。
- 普通文本会话仅在真实 DSH sessionId、当前账号身份、模型/推理/系统/工具配置及完整历史前缀均匹配时续接本插件创建的上游对话。缺少身份、图片输入、分支、编辑、压缩、失败、取消或状态过期时新建；不读取、接管或删除已有客户端历史。对话仍可能计入豆包历史。
- 请求停止/卸载时尽力取消本插件的上游流；若调试连接已经断开，无法保证服务器停止计费，界面会说明“结果不明”，不自动重发。
- 不导出/写入其他插件的配置、账号、余额或日志。

## Agent 查询工具

`doubao_client_status({ action: "status" | "quota" | "usage", days?: 1..90 })`

- `status`：连接、目录、额度、台账和能力边界。
- `quota`：仅查询真实额度。
- `usage`：仅读本地台账，days 指 UTC+8 日历日窗口。

与设置页使用同一个 Host 业务方法；工具不发送聊天、不重启、不登录、不提高权限。

## 配置与维护

插件 bundle 中的示例配置为：

```yaml
- insert:
    - id: doubao-client
      name: '@sanmumu/dsh-doubao-client'
      config:
        endpoint: 'http://127.0.0.1:19226'
        timeoutMs: 180000
        trustDeclaredWindow: true
        maxPromptChars: 400000
        maxOutputChars: 120000
        maxConcurrent: 2
        busyWaitMs: 20000
```

### 上下文窗口：标称配置不等于本插件实测容量

`trustDeclaredWindow: true` 时，DSH 的模型元数据使用客户端目录提供的 `model_extra_params.total_window_size`（当前为 256000 或 300000）。这是**客户端标称值**，不是本插件在普通对话传输中的实测容量；此配置只影响 DSH 的压缩规划，不会扩大上游窗口。

本地 `maxPromptChars: 400000` 按 JavaScript 字符串长度计量（UTF-16 代码单元，常见汉字通常占 1，部分 emoji 占 2）。超过时插件明确报 `DOUBAO_PROMPT_LIMIT`；低于此阈值也不保证上游会完整保留全部输入。字符数、UTF-8 字节数、token 数和解析后可检索文本不是可互换的单位，本项目不以字符数除以常数推算 token 窗口。

此前部分长文检索实验没有证明固定的模型 token 上限：测试重发新会话的整段文本，不是真实同会话累积；中文占位与英文输入表现不同；检索失败也不能单独区分上下文截断、服务端摘要/注入、文档解析覆盖或模型检索误差。因此撤回“普通对话约 2 万 tokens”“工作模式必然绑定更长上下文”“已达到 300k tokens”等结论。

普通对话的长文本附件链路已验证可上传、解析成功，并在约 12 万字符文档上取回首/中/尾随机记录；在 30 万与 60 万字符文档上仍出现只找回开头的情况。服务端解析状态为成功，但 `char_count` 返回 0，故它不能证明解析覆盖全文。60 万字符附件上的两轮 DSH 工具协议也完成了端到端验证，但这不等于完整 300k token 上下文已实现。

客户端 UI 的「工作任务」模式中，20 万及 60 万字符的测试文档能答出开头事实；60 万那次曾出现本机下载授权提示并被拒绝，随后模型报告改用只读方式读取。这证明 UI 路径可处理该测试，不证明模型原生上下文 token 数，也不代表插件普通对话路径具备相同能力。

状态中的 `contextWindowSource` 只表示 `client-declared`（采用客户端标称窗口）、`measured`（配置的覆盖值）或 `unknown/unverified`；`measured` 也只是配置来源标记，不是自动证明。需要以正式 DSH 路径、可靠 token 计量及首/中/尾判据继续验证后，才能声称具体可用容量。

这些上下限是本地字符/时间安全限制，不宣称是模型上下文或 token 上限。endpoint 仅接受 literal loopback HTTP origin，discovery 禁止重定向，并检查返回的 WebSocket 主机和端口。不要在个人 profile 内手工安装依赖或改写 bundle 状态；通过 DSH Plugin Manager 安装/禁用/卸载。

客户端更新导致内部模块 ID 或协议变化时，插件会报错，不尝试破解或自动降级到其它账户/模型。

## 1.7.0：有界并发与安全续接

- **已默认开启 2 路跨会话并发**（`maxConcurrent: 2`，允许整数 1–8；建议先保持 2）。同一 DSH 会话仍串行，避免同时修改同一上游续接历史。
- 全局槽位满后按 FIFO 等待 `busyWaitMs`（默认配置 20 秒）；身份/目录只读查询也通过相同槽位，避免第二会话在身份检查阶段被旧的全局忙锁挡住。状态的 `channel` 返回 `active`、`queued`、`maxConcurrent`、`quarantined`，不暴露请求正文或会话 ID。
- 每请求独立持有 CDP 连接、binding、解码器、取消句柄和一次性释放凭证。取消 A 不会终止 B；过期清理不能释放新请求的槽位。插件卸载会拒绝队列中的等待请求。
- 看门狗清理和正常清理共享同一个 Promise；会话锁等下游清理完成后才释放。被放弃的旧流即使重新读取也不会继续输出或提交续接映射。账号切换、forget 和新计划会使旧提交失效，图片/辅助调用也核对账号。
- **取消结果未知时不盲目补位**：若 CDP 已断开或远端取消未被确认，槽位进入 `quarantined`，避免上游旧生成可能仍在运行时超额发送。请先在豆包客户端确认旧请求结束，再重载插件；不自动重连重发。
- 并发共享同一账号订阅额度，不能绕过上游限流或 `710022004` 风控。以下 1.6.x 内容为历史变更记录；其中“全客户端单请求”已由本节的可配置并发上限取代。

- 续接使用 DSH `GenerateOptions.sessionId`，不根据首条用户消息猜测会话。只保留账号/配置/历史哈希和本插件收到的上游会话标识，不保留消息正文；最多 64 个会话，30 分钟未使用即失效，插件重载清空。标题、压缩请求和带图片历史保持独立请求。状态接口的 `continuity` 提供新建/续接尝试次数、带 ACK 确认完成的续接次数及最近降级原因，不暴露会话标识或正文。
- 账号来源经当前客户端 `UK -> Us.U.getState().userInfo.user_id_str` 契约核对；只在客户端内计算 SHA-256，再传不透明哈希。生成前、响应时检查账号一致性；账号缺失不续接，发送前发现换号则停止，不将旧历史发给新账号。
- 历史前缀与上轮实际输出匹配、服务端明确结束、工具封装验证通过后才提交续接映射。请求失败、取消、消费者提前结束会废弃映射。不会对未知结果自动重试或回退重发。
- 后端仍可解析上游 `context_window_usage`（设置页原「最近上下文遥测」展示卡片已按用户要求移除）。该数据与计费 tokens、订阅额度、标称窗口严格分开：缺失保持未知、不补零、不覆盖标称窗口，也不为采集它额外发送生成请求。观察到账号切换时清空旧的遥测与风控快照。
- `710022004` 归类为 `DOUBAO_RISK_CONTROL`，提示停止连续重试并在本人桌面客户端手动检查验证。不自动换模型、重登、破解验证、重试或设置未经上游确认的冷却倒计时。最近风控只是历史事件，不代表当前仍被封锁。
- 长文本附件、浏览器 Cookie 登录、原生任务执行、伪造操作成功回执均未并入。接口及安全性通过离线模拟回归；由于账号刚出现风控，本版没有发送真实模型续接/长文本压测请求，不能声称已线上验证续接或达到完整 256k/300k。
- **1.6.2 修正**：字符上限改为只约束**本次实际转交**的内容。已建立续接的会话只发送增量，因此历史累积超过上限后仍可继续对话（此前会误判为超限并每轮失败）。结构校验（不支持的块、工具封装）仍覆盖完整历史。
- **通道单请求闸与自愈（1.6.3）**：同一时刻只允许一个在途请求，第二个会得到「豆包通道正在处理请求，请稍后重试」（`DOUBAO_BUSY`）——这是刻意的，避免两个请求同时驱动客户端页面。若消费者中途不再读取流（页面刷新、回合被丢弃），生成器的 `finally` 永远不会执行；现在由看门狗兜底：**只在「已 yield 出去、等消费者继续取用」期间计时**（默认 60 秒，`abandonedConsumerMs` 可调），超时才取消远端、关闭连接并释放锁。等待上游首个事件或模型长时间静默**不会**被误判，慢生成仍正常保留。
- `doubao_client_status` 新增 `channel.busy` / `channel.busyForMs`，可区分「确有请求在跑」与「锁卡住」；后者会在阈值后自行恢复，不再需要重载插件。
- **忙时先排队（1.6.4）**：两道闸都改为「先短暂等待，再报错」。`busyWaitMs`（打包默认 20 秒，`0` = 立即报错）内若上一轮收尾就自动继续，超时仍明确报错：
  - 通道级 `DOUBAO_BUSY`（豆包通道正在处理请求）——同一客户端同时只跑一个请求；
  - 会话级 `DOUBAO_SESSION_BUSY`（该 DSH 会话仍有在途请求）——同一 DSH 会话不并发续接同一上游历史，避免续接状态被交错破坏。
  排队期间**不会**新建调试连接，也不会丢弃上一轮输出；等待可被取消立即打断。并发驱动客户端页面仍然是不允许的。
- **仍需注意的硬限制**：续接状态只在插件进程内，重载/重启/换账号/压缩或编辑分支后首轮必须发送完整历史。此时若完整历史超过 `maxPromptChars`，插件会明确报 `DOUBAO_PROMPT_LIMIT` 并提示压缩或新建会话——它不会静默截断。声明标称窗口会让 DSH 较晚压缩，所以长会话更容易累积到这个本地上限；需要减少历史时可手动执行 DSH `/compact` 或新建会话；下调 `maxPromptChars` 只会更早触发本地拒绝，不会自动让 DSH 提前压缩。
